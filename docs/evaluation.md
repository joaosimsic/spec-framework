# Evaluation

## Purpose

The framework should be judged by whether it reduces specification defects and review uncertainty, not by how impressive the generated document looks.

## Primary outcomes

| Outcome | Measurement |
|---|---|
| Gap detection | Number of undefined terms, dangling references, missing relations, unanswered edge cases, and unverified requirements found before implementation |
| Traceability | Percentage of approved requirements linked to architecture, formalization, contract, and code/test evidence |
| Review time | Time for a human to audit a change end to end using the bundle and change report |
| Rework | Number of specification changes caused by defects discovered after implementation |
| Drift | Number of code-to-spec mismatches detected in CI |
| Formal coverage | Percentage of approved behavioral requirements model-checked or explicitly waived |
| Reproducibility | Percentage of bundles regenerated byte-for-byte or semantically identical from a clean checkout |

## Leading indicators

- Unknowns are filed rather than guessed.
- Waivers have owners and expiries.
- Agents pass validators before requesting review.
- Humans approve diffs, not prose.
- The default agent has zero writes to approved content.
- The audit bundle contains no hand-edited generated sections.

## Setup and adoption

| Measure | Target |
|---|---|
| Time from clone to structural gap report | under 1 minute |
| Manual setup steps for full stack | zero beyond `spec init` and `spec doctor --fix` |
| Missing-tool failures resolved by doctor | tracked per run |
| Existing repo initialized without source changes | 100% |
| Mapping elements requiring human correction | tracked; should trend down with adapters |

Full-stack provisioning time is measured separately from time-to-first-value. Slow provisioning is visible, but it does not block fast structural feedback.

## Anti-metrics

Avoid:

- number of pages in the specification;
- number of generated tasks;
- LLM token usage;
- percentage of text written by the agent;
- "spec completeness score" without a defined question matrix;
- formal lines of code without a property list.

## Experiments

### Experiment 1: prose vs typed spec

Take one real feature. Write the conventional prose spec, then the typed spec. Compare defects found by reviewers and time to audit.

### Experiment 2: agent with and without gates

Have an agent implement the same approved feature with and without the validation and approval gates. Compare architectural drift, missed requirements, and rework.

### Experiment 3: formal feedback loop

Ask the agent to write Quint properties for ten requirements. Measure how many pass type checking and model checking on the first attempt, after repair loops, and after human review.

### Experiment 4: non-web coverage

Apply the framework to a library, a CLI, a file format, and a device protocol. Identify which contract adapters are genuinely reusable and which are project-specific.

## Success criteria for the framework itself

- A new project can be bootstrapped without editing the framework core.
- Every gate has a failing fixture and a passing fixture.
- The audit bundle can be produced from a clean git commit without network access beyond pinned dependencies.
- A human can identify all unverified requirements, unknowns, and waivers from the bundle alone.
- Removing the LLM does not break any verification step.

## Failure criteria

- Reviewers must read DSL or formal code to find basic gaps.
- The bundle is partially hand-written.
- Approval can be bypassed by editing hashes.
- The framework only works for HTTP services.
- Formal verification is claimed but not reproducible.
- The agent becomes the only entity that understands the spec.
