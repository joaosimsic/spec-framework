# Evaluation

## Purpose

The framework is judged by whether generated output helps a human understand an
unfamiliar repository and locate architectural problems without hand-maintained
documentation.

## Primary outcomes

| Outcome                | Measurement                                                                 |
| ---------------------- | --------------------------------------------------------------------------- |
| Architecture accuracy  | Generated subsystem/component hierarchy matches repository structure        |
| Code traceability      | Percentage of generated elements linked to files and symbols                |
| Flow coverage          | Percentage of detected entry points with bounded static paths               |
| Uncertainty visibility | Percentage of unresolved calls, ambiguous edges, and missing tests reported |
| Diagnostic usefulness  | Percentage of deterministic findings accepted for investigation             |
| Snapshot determinism   | Byte-identical output for the same commit and versions                      |
| Review time            | Time to answer “what does this system do and where should I look?”          |
| Migration completeness | Curated spec reads removed from workbench and query paths                   |

## Leading indicators

- The workbench opens on System with no curated model present.
- Every generated node cites provenance.
- Unknowns are visible rather than hidden.
- Snapshot comparison shows meaningful architecture change.
- AI can be removed without changing deterministic output.
- No generated record claims approval.

## Anti-metrics

Avoid:

- number of generated pages;
- number of generated findings without triage;
- LLM token usage;
- percentage of text generated by AI;
- “spec completeness” without defined evidence;
- lines of formal code without a property list.

## Experiments

### Experiment 1: unfamiliar repository

Give an engineer an unfamiliar TypeScript repository. Compare time to explain
its architecture with and without the generated System view.

### Experiment 2: curated versus generated

Compare maintenance effort and drift between a hand-authored architecture model
and the generated architecture for the same repository over several commits.

### Experiment 3: finding quality

Have maintainers triage deterministic findings. Measure accepted, rejected, and
needs-investigation rates.

### Experiment 4: AI without authority

Test whether AI explanations cite valid evidence and whether invalid references
are rejected. Compare review confidence with and without AI.

## External validation

Results for `boring`, `llm-ruler`, and `TiCrafter` are recorded in
[Generated spec validation](validation/generated-spec-validation.md).

Measured outcomes:

- analysis: 2.20s to 54.58s;
- graph depth 2 median: 1ms to 4ms;
- graph depth 4 median: 1ms to 8ms;
- deterministic output: yes;
- original repositories modified: no.

## Success criteria

- Behavior-derived conceptual architecture is coherent for a real repository.
- Entry points and flows are useful without manual modeling.
- Findings have actionable evidence.
- Snapshots reproduce deterministically.
- Workbench and query consume conceptual architecture plus explicit implementation mappings.
- Removing AI does not break analysis or review.

## Failure criteria

- Generated output requires hand correction to be useful.
- Conceptual hierarchy is directory-derived, arbitrary, or unstable across renames.
- Findings are mostly noise.
- Workbench depends on curated spec sources.
- Generated records imply approval or completeness.
- The product only works for HTTP services.
